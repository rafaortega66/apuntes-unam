Documentación de The Open Group y la función socket()

La sesión empezó revisando la documentación oficial en el sitio de The Open Group (opengroup.org). El profesor recomendó una buena práctica: buscar directamente el nombre de la función en el navegador para llegar a la especificación estándar POSIX, en inglés técnico. Se retomó la Clase 09 (struct hostent, gethostbyname(), conversiones de IP, puertos de la IANA y la introducción teórica al ciclo de vida de los sockets) para ahora implementar el lado del servidor.

La primera función del servidor es socket(), declarada en <sys/socket.h>. Su propósito formal es crear un extremo no ligado (unbound) de un canal de comunicación:

int socket(int domain, int type, int protocol);
ArgumentoQué especifica
domain (familia)Dominio o familia de direcciones. Se usa AF_INET (IPv4). Otras: AF_INET6, AF_UNIX / AF_LOCAL (comunicación local entre procesos de la misma máquina), AF_BLUETOOTH, AF_PACKET.
typeEsquema de transporte. SOCK_STREAM para TCP (orientado a conexión y confiable); SOCK_DGRAM para UDP (datagramas no confiables). También existen SOCK_SEQPACKET y SOCK_RAW.
protocolProtocolo particular de la familia. Con 0 el sistema elige el protocolo por defecto para esa combinación (para AF_INET + SOCK_STREAM, TCP/IP). También puede ponerse IPPROTO_TCP.

Valor de retorno. Si tiene éxito, devuelve un entero no negativo: el descriptor de archivo (fd) del socket. Como 0, 1 y 2 están reservados para stdin, stdout y stderr, el primer socket de un programa suele recibir el 3. Si falla, devuelve -1 y deja el código de error en la variable global errno. Ese descriptor se pasa como primer argumento a todas las funciones siguientes (bind, listen, accept).

Explicado en simple

Es como solicitar una línea telefónica nueva a la compañía; obtienes un aparato telefónico sin número asignado que te sirve como punto de acceso para hacer y recibir llamadas.Dónde falla la analogía: En la telefonía real el teléfono ya tiene una clavija física, mientras que en C el socket es puramente un número entero de software (file descriptor) dentro del sistema operativo.

Por qué importa / con qué se conecta

Es la primera función para crear un extremo de comunicación; recibe el dominio (AF_INET), el tipo (SOCK_STREAM para TCP) y el protocolo (0), devolviendo un descriptor entero (habitualmente 3) indispensable para las funciones siguientes.

Errores comunes: Confundir las macros de dominio y tipo o no validar que el valor de retorno sea distinto de -1 para detectar errores en la creación del socket.

Inicialización de struct sockaddr_in (paso intermedio)

Entre socket() y bind() es obligatorio inicializar la estructura de dirección del servidor, declarada como struct sockaddr_in servidor;. Si no se configura bien, las llamadas posteriores fallan y el servidor no arranca. En el Programa 04 del profesor (004_servidor.c) los pasos son:

  1. Limpiar la memoria con memset(), para eliminar valores basura: 
    memset(&servidor, 0, sizeof(servidor));
  2. Familia (sin_family): debe coincidir exactamente con el dominio usado en socket(): 
    servidor.sin_family = AF_INET;
  3. Dirección IP (sin_addr.s_addr): lleva dos puntos porque servidor es un struct sockaddr_in cuyo atributo sin_addr es a su vez una estructura anidada de tipo struct in_addr; para llegar a s_addr (la IP binaria de 32 bits) se necesita un segundo punto, como acceder al atributo de un atributo en programación orientada a objetos: 
    servidor.sin_addr.s_addr = INADDR_ANY;
  4. Puerto (sin_port) con htons(): el ejemplo usa el puerto 4898. Los humanos escribimos el puerto en decimal, pero el hardware y los protocolos de red lo procesan en binario con orden de bytes de red (network byte order), por eso se aplica htons(): 
    servidor.sin_port = htons(4898);
    La nemotecnia: H = Host, N = Network, T = To (“hacia”), S = Short (entero corto de 16 bits sin signo, adecuado para puertos).
  5. Relleno (sin_zero): arreglo de 8 caracteres en cero que existe por razones históricas para igualar el tamaño de struct sockaddr_in con el de la estructura genérica struct sockaddr. En Linux moderno es opcional, pero se pone explícitamente en ceros: 
    memset(servidor.sin_zero, '\0', 8);

¿Por qué el servidor especifica una IP y qué significa INADDR_ANY? El profesor lo planteó como pregunta: si el cliente es quien busca al servidor, ¿por qué el servidor define una IP? Porque un equipo puede tener varias interfaces de red (Ethernet, Wi-Fi, loopback 127.0.0.1, adaptadores virtuales). Con INADDR_ANY el servidor le indica al sistema operativo que escuchará las peticiones que lleguen por todas las direcciones IP de todas las interfaces. Así un cliente local puede conectarse por 127.0.0.1 y uno externo por la IP pública o privada de la tarjeta de red.

Explicado en simple

Es como llenar una ficha con tu dirección de casa y tu número de departamento antes de poner un letrero en la puerta, para que el correo sepa exactamente dónde entregarte los paquetes.Dónde falla la analogía: En una casa física solo hay una puerta, mientras que en un servidor de software hay múltiples tarjetas de red físicas y virtuales, y la ficha debe abarcar todas mediante INADDR_ANY.

Por qué importa / con qué se conecta

Es el paso intermedio imprescindible entre socket() y bind(); se limpia con memset(), se asigna AF_INET, se usa el doble punto servidor.sin_addr.s_addr = INADDR_ANY para escuchar en todas las interfaces de red, y htons() para convertir el puerto a binario de red.

Errores comunes: Olvidar el doble operador punto al acceder a s_addr dentro de sin_addr, no usar htons() en el puerto, o dudar de por qué el servidor necesita una IP si es el cliente quien lo busca.

La función bind()

bind se traduce como “ligar”, “asociar” o “nombrar” el socket. En sockets de Internet (AF_INET), nombrar un socket significa vincular de forma definitiva el descriptor devuelto por socket() con una IP y un puerto concretos.

int bind(int socket, const struct sockaddr *address, socklen_t address_len);
  • socket: el descriptor devuelto por socket() (fd_s).
  • address: apuntador al tipo genérico struct sockaddr *. Como se usa struct sockaddr_in, se pasa la dirección de la estructura con un cast explícito: (struct sockaddr *) &servidor.
  • address_len: tamaño en bytes de la estructura, con sizeof(servidor).

Invocación exacta en 004_servidor.c:

if (bind(fd_s, (struct sockaddr *) &servidor, sizeof(servidor)) == -1) {
    perror("bind");
    exit(EXIT_FAILURE);
}

Permisos de puerto. Los puertos menores a 1024 están reservados para el administrador (root / sudo). Un usuario sin privilegios solo puede hacer bind() en el rango 1024 a 65535 y solo si el puerto no lo ocupa otro proceso.

Explicado en simple

Es como clavar un letrero con el nombre de tu negocio y tu número de local en la puerta de entrada para que la gente sepa qué servicio atiende ahí.Dónde falla la analogía: Un letrero físico lo puede poner cualquiera, pero en sistemas los puertos menores a 1024 requieren permisos de administrador (root/sudo) para poder ligarlos.

Por qué importa / con qué se conecta

Asocia o "liga" el descriptor del socket (fd_s) devuelto por socket() con la IP y el puerto de la estructura sockaddr_in; recibe el fd, el apuntador casteado a (struct sockaddr *) y su tamaño.

Errores comunes: Intentar hacer bind() en puertos reservados (0-1023) sin privilegios de root o no realizar el cast explícito de tipo de estructura.

listen(), la cola de conexiones (backlog) y el saludo de tres vías

listen() pone el socket en modo de escucha activa para atender solicitudes de conexión:

int listen(int socket, int backlog);

socket es el descriptor del socket servidor (fd_s) y backlog es el número máximo de conexiones entrantes pendientes que el sistema mantiene en la cola de espera.

Cómo funciona la cola. Al arrancar, la cola está vacía. La primera petición de un cliente entra a la cola y el servidor la atiende de inmediato. Si llegan más peticiones mientras el servidor está ocupado con la primera, esos clientes quedan encolados esperando; backlog define el límite de esa cola. Detrás del encolamiento está el establecimiento de conexión TCP conocido como saludo de tres vías (three-way handshake: paquetes SYN, SYN-ACK y ACK).

Explicado en simple

Es como abrir la puerta del negocio, encender la luz de "abierto" y colocar un cordón de fila para organizar a los clientes que vayan llegando.Dónde falla la analogía: En una fila física la gente se ve parada, pero en TCP el backlog gestiona en silencio la cola de conexiones pendientes mediante el saludo de tres vías (three-way handshake).

Por qué importa / con qué se conecta

Coloca el socket servidor en modo de escucha activa y define el tamaño máximo de la cola de conexiones pendientes (backlog) antes de pasarlas a accept().

Errores comunes: Confundir el parámetro backlog con el número total de clientes atendidos en la vida útil del servidor en lugar de la cola en espera.

accept() y los dos sockets del servidor

Después de listen(), el servidor llama a accept(), una llamada bloqueante: detiene la ejecución hasta que un cliente intenta conectarse y la conexión se extrae de la cola de listen().

int accept(int socket, struct sockaddr *restrict address, socklen_t *restrict address_len);
  • socket: el descriptor del socket servidor (fd_s).
  • address: apuntador a struct sockaddr * (en la práctica (struct sockaddr *) &cliente), que el kernel rellena automáticamente con la IP y el puerto del cliente que se conecta.
  • address_len: apuntador a una variable con el tamaño de la estructura del cliente (&longitud_cliente).

La clave de la arquitectura cliente-servidor. El profesor enfatizó que entender accept() es la base de todo el curso: todo servidor maneja al menos dos sockets independientes.

Pregunta de una alumna: ¿Un mismo cliente puede conectarse a varios servidores al mismo tiempo? Respuesta del profesor: sí, es una observación perfectamente válida. Ejemplos: un sistema de bases de datos distribuidas o una aplicación empresarial que consume datos de tres servidores de base de datos en hosts distintos; o un cliente conectado a la vez a un servidor web (puerto 443), a uno de base de datos MySQL (3306) y a uno de correo SMTP (25). En ese caso el proceso cliente debe crear tres estructuras struct sockaddr_in independientes y tres sockets distintos, uno por servicio.

Explicado en simple

Es como el recepcionista que toma al primer cliente de la fila de espera y lo asigna a un cubículo privado con un ejecutivo dedicado para que hablen sin bloquear la puerta principal.Dónde falla la analogía: En el cubículo físico la persona camina a otra habitación, pero en software el servidor crea un nuevo entero de socket (fd_c) en la misma memoria para el flujo de datos.

Por qué importa / con qué se conecta

Es una función bloqueante que acepta la conexión entrante y devuelve un nuevo descriptor de socket (fd_c), dividiendo la arquitectura en socket de conexión (fd_s) y socket de comunicación (fd_c).

Por qué el servidor hace dos close() y el ciclo secuencial

Al revisar el cierre de sockets se explicó por qué el cliente llama una sola vez a close() y el servidor dos:

  • Cliente: close(fd) cierra su único socket.
  • Servidor secuencial (no concurrente): atiende a un cliente a la vez. Intercambia datos con fd_c y, cuando el cliente termina, cierra ese socket con el primer close(fd_c). Luego, con un bucle, regresa a accept() a esperar al siguiente cliente de la cola. Solo cuando el servidor se apaga por completo se ejecuta el segundo close(fd_s), que libera el socket servidor y termina el proceso.
Explicado en simple

Es como colgar el teléfono de la extensión del cliente cuando termina de hacer su pedido, mientras la centralita telefónica principal sigue encendida esperando la llamada del siguiente cliente.Dónde falla la analogía: Colgar un teléfono desconecta el cable, pero en software close() destruye el descriptor de archivo en la tabla de procesos de Linux.

Por qué importa / con qué se conecta

Explica por qué el servidor ejecuta dos close(): primero cierra el socket cliente (fd_c) al terminar la sesión y regresa cíclicamente a accept(), y solo cierra el socket servidor (fd_s) al apagar el servicio.

Errores comunes: Creer que con un solo close() se cierran ambos sockets en el servidor, o no entender el ciclo de recursividad de un servidor secuencial.

🧠 Ponte a prueba

Intenta contestar cada pregunta antes de abrirla. Recordar por tu cuenta es lo que fija la información; releer no la fija.

1. ¿Qué valor de descriptor de archivo entero devuelve habitualmente la función socket() si es el primer socket creado en el programa y por qué?

Devuelve el entero 3, porque los descriptores 0, 1 y 2 están previamente reservados por el sistema operativo para la entrada estándar (stdin), salida estándar (stdout) y salida de error (stderr).

2. Explica con tus palabras por qué el servidor utiliza la macro INADDR_ANY al inicializar la estructura struct sockaddr_in.

Porque un host puede tener múltiples interfaces de red (Wi-Fi, Ethernet, loopback o virtuales) e INADDR_ANY le indica al sistema que acepte conexiones dirigidas a cualquiera de sus direcciones IP disponibles.

3. Si deseas configurar un servidor para que escuche en el puerto 5000, ¿cómo debes asignar dicho puerto al atributo sin_port en C?

Se debe asignar utilizando la función de conversión de orden de bytes htons(5000), escribiendo servidor.sin_port = htons(5000).

4. Compara la función del socket servidor (fd_s) con la del socket cliente devuelto por accept() (fd_c) dentro del servidor.

El socket servidor (fd_s) es el socket de conexión que escucha y encola peticiones en la IP/puerto del servidor, mientras que fd_c es el socket de comunicación dedicado exclusivamente a intercambiar datos con el cliente aceptado.

5. ¿Qué ocurre si un usuario normal sin privilegios de root intenta ejecutar un programa servidor que hace bind() en el puerto 80?

La llamada a bind() fallará y devolverá -1, ya que todos los puertos del 0 al 1023 están reservados exclusivamente para el usuario administrador (root / sudo).

6. Explica el papel que desempeña el parámetro backlog en la función listen().

Define la cantidad máxima de solicitudes de conexión entrantes pendientes que el sistema operativo mantendrá en la cola de espera mientras son procesadas por accept().

7. ¿Por qué el proceso servidor ejecuta dos llamadas a la función close() mientras que el cliente solo ejecuta una?

Porque el cliente solo tiene su socket de comunicación, mientras que el servidor debe cerrar primero el socket del cliente aceptado (fd_c) para atender al siguiente y, finalmente, el socket servidor (fd_s) al apagar el servicio.

8. Un programa servidor ejecuta socket() y obtiene fd_s = 3. Luego acepta un cliente con accept(). ¿Qué valor entero tendrá el descriptor devuelto por accept() y para qué se usará?

Será el siguiente descriptor libre (normalmente 4, porque 0, 1, 2 y 3 ya están ocupados); es fd_c y se utilizará como parámetro en las funciones de lectura/escritura (read/write o send/recv) para el intercambio de datos con ese cliente.

Puntos clave

  • socket(domain, type, protocol) crea un socket no ligado y devuelve un descriptor (habitualmente 3): AF_INET para IPv4 y SOCK_STREAM para TCP.
  • Antes de bind() se limpia struct sockaddr_in con memset(), se usa INADDR_ANY en sin_addr.s_addr para escuchar en todas las interfaces y htons() en el puerto.
  • bind() liga el descriptor con la IP y el puerto; listen() lo pone a escuchar y fija el límite de la cola (backlog).
  • accept() es bloqueante y devuelve un nuevo descriptor (fd_c) para el cliente aceptado.
  • Todo servidor maneja dos sockets (fd_s y fd_c), por eso lleva dos close().
