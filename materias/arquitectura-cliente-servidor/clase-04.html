strerror() y los códigos de error de Linux

strerror(n) — "devuelve el mensaje de sistema correspondiente al código que le pasas como parámetro". El prefijo str es por string: devuelve la cadena de texto asociada al código numérico. Análisis de programa03_codigos_sistema.c:

int i;
for (i = 0; i <= 150; i++)          /* el límite se puede subir a 200 para probar */
    printf("%d: %s\n", i, strerror(i));

%d (o %i) se reemplaza con el entero i; %s con el string que devuelve strerror(i).

  • Las distros comunes traen entre 130 y 133 códigos de error. En el entorno de clase (Fedora / Red Hat) el último con mensaje válido es el 133; a partir del 134 se imprime Unknown error.
  • En Fedora, el código 41 no tiene error asociado — está reservado / saltado para implementaciones futuras.
Explicado en simple

Es como un diccionario que traduce un código de falla numérico a una frase descriptiva en texto para entender qué salió mal.Dónde falla la analogía: El diccionario impreso tiene palabras fijas, pero strerror() consulta arreglos internos del sistema operativo donde el código 0 es éxito y los errores válidos llegan hasta el 133.

Por qué importa / con qué se conecta

Permite recorrer con un bucle for los códigos enteros de error e imprimir la cadena explicativa correspondiente retornada por strerror(i), mostrando que a partir del 134 devuelve error desconocido.

Errores comunes: Creer que el entero 0 representa un error en Linux, cuando el profesor aclaró que 0 significa ejecución exitosa (Success).

perror() — mensaje de error personalizado

Recibe una cadena personalizada; si la instrucción anterior generó error, perror toma esa cadena, le añade automáticamente ": " y concatena a la derecha el mensaje de error estándar del sistema. La P es de "personalizar".

Ejemplo: si un fork() falla, perror("fork") imprime fork: <mensaje del sistema>.

Explicado en simple

Es como poner una etiqueta con tu nombre en una caja de herramientas para que, si falla, el sistema le agregue la explicación técnica justo después de dos puntos.Dónde falla la analogía: La etiqueta de papel no cambia, pero perror() lee automáticamente la variable global errno del sistema para adjuntar la causa real de la falla.

Por qué importa / con qué se conecta

Permite personalizar los mensajes de error en C anteponiendo una cadena definida por el usuario (como perror("fork")) seguida de dos puntos y el mensaje descriptivo provisto por errno.

Control de flujo de fork()

Con condicionales, fork() abre tres caminos: el de error, el del hijo y el del padre.

Estilo compacto (paréntesis anidados):

if ((child = fork()) == -1) { ... }

El compilador lo resuelve así: 1) se invoca fork(); 2) su valor de retorno se asigna a child; 3) se compara child con -1.

Estilo descompuesto ("camino largo", prioriza claridad sobre rendimiento):

pid_t ch;
ch = fork();
if (ch == -1) { ... }
Explicado en simple

Es como un desvío en una carretera con tres carriles: uno si el camino se rompió, otro para el auto clonado y otro para el auto original.Dónde falla la analogía: En la carretera los autos son vehículos separados, pero en C fork() crea una copia en memoria y evalúa todo en una misma línea con paréntesis anidados.

Por qué importa / con qué se conecta

Muestra cómo evaluar en un condicional if/else if/else los tres flujos de fork() desglosando los tres pasos: llamada a la función, asignación de derecha a izquierda a la variable y comparación contra -1.

Errores comunes: Confundir el operador de asignación simple (=) dentro del paréntesis anidado con el operador de comparación de igualdad (==).

Documentación oficial y retorno de fork()
  • Para llegar al sitio oficial, buscar en Google: "Open Group" fork → www.opengroup.org.
  • fork(), getpid(), getppid(), getuid(), geteuid(), getgid(), getegid() están definidas en <unistd.h>.
  • fork() devuelve pid_t, que internamente es un entero → se imprime con %d.
  • Éxito: devuelve 0 al hijo y el PID del hijo al padre; ambos siguen ejecutando en paralelo las líneas posteriores.
  • Error: devuelve -1 al padre, no se crea hijo y se establece errno. Causa más común: falta de memoria para duplicar la imagen del proceso.
Explicado en simple

Es como consultar el manual de usuario oficial de un electrodoméstico en internet para verificar qué tipo de clavija usa y qué respuestas puede darte.Dónde falla la analogía: El manual de un aparato describe piezas físicas, mientras que la documentación de Open Group especifica la librería unistd.h, el tipo pid_t y los valores de retorno del kernel.

Por qué importa / con qué se conecta

Se utiliza la búsqueda en Open Group para consultar la definición formal de fork(), la cabecera unistd.h, el tipo de dato pid_t y las razones por las que puede fallar retornando -1 (como falta de memoria RAM).

exit() y macros de salida

Cuando una llamada crítica (fork(), exec()) devuelve -1, se usa exit() para terminar el programa de inmediato y no seguir ejecutando código.

  • EXIT_FAILURE (en mayúsculas) ≡ exit(1) — salida no exitosa.
  • EXIT_SUCCESS ≡ exit(0) — salida exitosa.
Explicado en simple

Es como presionar el botón de paro de emergencia en una fábrica para detener todo si ocurre un fallo o el botón de apagado normal al terminar el turno.Dónde falla la analogía: Los botones de la fábrica cortan la electricidad, pero exit() en C envía una macro estandarizada de terminación al sistema operativo.

Por qué importa / con qué se conecta

Permite finalizar la ejecución de un proceso devolviendo macros formales de stdlib.h: EXIT_FAILURE (equivalente a exit(1)) para fallos y EXIT_SUCCESS (equivalente a exit(0)) para terminación limpia.

Errores comunes: Usar valores numéricos fijos o no invocar exit() inmediatamente después de detectar un error grave en llamadas al sistema.

Procesos huérfanos, adopción y reapers

Al correr programa08, la salida muestra in parent antes que in child, y el hijo, al llamar getppid(), obtiene 1 aunque su padre real era otro.

  • Proceso huérfano: "un proceso cuyo padre ya murió, pero él sigue vivo". Aquí el padre terminó antes de que el hijo llegara a getppid().
  • Linux no permite huérfanos sin control: el proceso PID 1 (init en sistemas antiguos, systemd en modernos) los adopta automáticamente.
  • En distros modernas hay subprocesos monitores llamados reapers ("recogedores") que adoptan y vigilan huérfanos para descargar al PID 1 → por eso a veces el PPID de adopción que ves no es 1.
  • Ver la distro exacta: cat /etc/os-release (la máquina del profesor: Fedora Linux Workstation 40).
  • Jerarquía familiar: el proceso creado es el hijo; el que llamó fork() es el padre; la terminal interactiva es el abuelo.
Explicado en simple

Es como cuando un polluelo queda sin su mamá e inmediatamente es adoptado por una granja protectora para que no ande solo por el campo.Dónde falla la analogía: El polluelo camina por la granja, pero en Linux un proceso huérfano es reasignado en la tabla de procesos al PID 1 (init/systemd) o a subprocesos reapers para limpiar su memoria.

Por qué importa / con qué se conecta

Define formalmente qué es un proceso huérfano (aquel cuyo padre muere antes que él), demostrando en vivo que al llamar getppid() el hijo obtiene PID 1 o el PID de un reaper, verificado con cat /etc/os-release.

Errores comunes: Sorprenderse si en distribuciones modernas como Fedora el proceso adoptante no tiene PID 1, ya que el profesor explicó que se usan subprocesos reapers para no sobrecargar a init.

La familia de funciones exec

No existe exec "a secas": es una familia de seis funciones que empiezan con esa palabra y añaden 1 o 2 letras que definen su comportamiento.

LetraSignificado
L (list)Los argumentos se escriben como lista explícita separada por comas, terminada en NULL o (char *)0.
V (vector)Los argumentos van en un arreglo de punteros, también terminado en puntero nulo.
E (environment)Permite pasar un vector de variables de entorno propias, válidas solo durante la ejecución del nuevo proceso.
P (PATH)No requiere ruta absoluta: lee la variable PATH y busca el ejecutable en los directorios del sistema (/bin, /usr/bin…).
  • execl, execv, execle, execve → parámetro path (ruta absoluta, ej. /bin/ls).
  • execlp, execvp → parámetro file (nombre a secas, ej. ls).
Explicado en simple

Es como una navaja suiza que tiene seis herramientas diferentes para realizar la misma tarea de reemplazo, según cómo le pases los materiales.Dónde falla la analogía: La navaja realiza cortes físicos, mientras que las seis funciones exec modifican la estructura de ejecución de memoria del proceso en Linux.

Por qué importa / con qué se conecta

Presenta las seis funciones de la familia exec (execl, execv, execle, execve, execlp, execvp) explicando la nemotecnia de sus letras: l para listas terminadas en NULL, v para vectores, e para variables de entorno y p para búsqueda en el PATH.

Errores comunes: Creer que exec es una sola función en C en lugar de una familia de seis funciones distintas.

Reemplazo de imagen y "argumento cero"

A diferencia de fork() (que duplica), cuando exec tiene éxito la imagen del proceso original en memoria se destruye y se reemplaza por completo por la del nuevo programa. El proceso original muere en ese punto y no recupera el control.

En C, argv[0] debe ser el nombre del ejecutable, por eso la cadena del comando aparece repetida:

execl("/bin/ls", "ls", "-l", "/", (char *)0);
/*     ^ruta      ^arg0 ^arg1 ^arg2  ^fin de lista */
Explicado en simple

Es como cambiar el actor de una obra de teatro a mitad de la función: la obra sigue en el mismo escenario con el mismo número de camerino, pero el guión y el personaje son totalmente nuevos.Dónde falla la analogía: En el teatro el actor anterior sale caminando a vestidores, pero en exec la imagen del proceso original es sobreescrita por completo en memoria manteniendo únicamente el mismo PID.

Por qué importa / con qué se conecta

Explica que exec sobreescribe la memoria del proceso llamador por el nuevo ejecutable sin crear un nuevo PID, y muestra por qué el argumento cero (argv) repite el nombre del comando como en execl("/bin/ls", "ls", "-l", "/", NULL).

Errores comunes: Olvidar repetir el nombre del ejecutable como argumento cero o no finalizar la lista de argumentos explícitamente con un puntero NULL.

Manejo de errores y código inalcanzable

Si el comando no existe o está mal escrito, exec falla, devuelve -1 y el proceso original sigue ejecutando las líneas de abajo. En una llamada exitosa, en cambio, esas líneas son inalcanzables (el proceso ya fue reemplazado).

Regla obligatoria — envolver en if y terminar si devuelve -1:

if (execl("/bin/ls", "ls", "-l", "/", (char *)0) == -1) {
    perror("execl");
    exit(EXIT_FAILURE);
}
Explicado en simple

Es como poner una puerta de seguridad con cerrojo automático: si la puerta se abre la persona pasa al nuevo cuarto, pero si falla el cerrojo se activa la alarma y se evacúa de inmediato.Dónde falla la analogía: La puerta de seguridad se puede abrir y cerrar varias veces, mientras que si exec tiene éxito nunca regresa al código anterior.

Por qué importa / con qué se conecta

Establece la buena práctica de colocar la llamada a exec dentro de un if evaluado contra -1 y terminado en exit(EXIT_FAILURE), demostrando que cualquier código posterior a exec es inalcanzable si exec funciona.

Errores comunes: Permitir que el proceso original continúe ejecutándose si exec falla por haber omitido el exit() dentro del bloque de manejo de errores.

gcc programa10.c -o programa10

  • Prueba 2 (error intencional): se cambia el comando a /bin/lsa (no existe) y se comenta el exit(EXIT_FAILURE). Resultado: execl devuelve -1, perror("execl") imprime execl: No such file or directory y, como no hay exit, el proceso sigue vivo e imprime "esto no se imprime" — mostrando físicamente la falla por no manejar el error.
Explicado en simple

Es como hacer un simulacro de accidente donde a propósito se usa una ruta falsa para comprobar si los frenos de emergencia funcionan como se planeó.Dónde falla la analogía: El simulacro usa vehículos reales, mientras que en la terminal se prueba la sustitución de código en C modificando cadenas de texto en el archivo fuente.

Por qué importa / con qué se conecta

Se demuestra en vivo en la terminal la ejecución de programa10.c cambiando /bin/ls por /bin/lsa y comentando exit(); la terminal imprimió perror ("No tal archivo o directorio") y la frase "esto no se imprime", evidenciando un mal manejo de errores.

Errores comunes: Dejar sin comentar o no verificar las frases impresas tras un fallo deliberado de exec, lo que demuestra que el proceso original sobrevivió por falta de exit().

🧠 Ponte a prueba

Intenta contestar cada pregunta antes de abrirla. Recordar por tu cuenta es lo que fija la información; releer no la fija.

1. ¿Qué valor de retorno de la función strerror(i) indica el límite de los códigos de error válidos en la distribución de Linux probada en clase?

A partir del código entero 134, strerror() devuelve la cadena "Unknown error" o "Error desconocido", siendo el 133 el último código con mensaje válido de sistema.

2. Explica con tus palabras la diferencia principal entre la función strerror() y la función perror().

strerror() recibe un número entero de error y devuelve su cadena descriptiva de sistema, mientras que perror() recibe una cadena personalizada del usuario, la antepone seguida de dos puntos y le anexa el mensaje de error provisto por errno.

3. Explica el orden de ejecución de los tres pasos presentes en la expresión condicional con paréntesis anidados if ((child = fork()) == -1).

Primero se ejecuta la llamada a fork(), segundo el valor retornado por fork() se asigna de derecha a izquierda a la variable child mediante un solo signo igual, y tercero se compara el valor almacenado en child contra -1 mediante el operador de doble igual.

4. Compara el comportamiento de la función fork() con el de la familia de funciones exec en cuanto a la creación de procesos y asignación de PIDs.

fork() duplica el proceso actual creando un proceso hijo en paralelo con un nuevo PID, mientras que exec sobreescribe por completo la imagen de memoria del proceso llamador por un nuevo ejecutable conservando el mismo PID.

5. ¿Qué le sucede a un proceso hijo si su proceso padre muere antes que él y qué proceso lo adopta en el sistema operativo?

Se convierte en un proceso huérfano y es adoptado automáticamente por el proceso init/systemd (con PID 1) o por subprocesos especializados llamados reapers para limpiar su entrada en la tabla de procesos.

6. Un programa ejecuta la llamada execl("/bin/ls", "ls", "-l", "/home", NULL). ¿Cuál es la función del segundo parámetro "ls" en esta llamada?

Corresponde al argumento cero (argv), el cual por convención en lenguaje C debe ser el propio nombre del comando o programa ejecutable que se va a invocar.

7. ¿Por qué se afirma que las líneas de código colocadas físicamente después de una llamada exitosa a exec representan código inalcanzable?

Porque si exec tiene éxito, la imagen de memoria del proceso llamador es sobreescrita por completo por el nuevo programa, por lo que las instrucciones subsecuentes del archivo original dejan de existir en memoria.

8. Un estudiante escribe el siguiente código: if (execl("/bin/lsa", "lsa", NULL) == -1) { perror("execl"); } printf("Proceso terminadon");. ¿Qué error de programación señaló el profesor sobre este esquema cuando exec falla?

Omitió la instrucción exit(EXIT_FAILURE) dentro del bloque if, lo que provoca que cuando exec falla el proceso original no se aborte y continúe ejecutando indebidamente las líneas posteriores como el printf.

Puntos clave

  • strerror(n) devuelve la cadena del mensaje de sistema para el código n; perror("txt") imprime txt: <mensaje del sistema> si la instrucción anterior falló.
  • fork() abre tres caminos: error (-1), hijo (0) y padre (PID del hijo) — la causa más común de -1 es falta de memoria para duplicar la imagen del proceso.
  • Un proceso huérfano (padre ya muerto) es adoptado por PID 1 o por un reaper en distros modernas.
  • La familia exec tiene 6 funciones (L/V/E/P combinables); si tiene éxito reemplaza la imagen del proceso — el código posterior es inalcanzable — y si falla hay que envolverla siempre en if (... == -1) { perror(...); exit(EXIT_FAILURE); }.
