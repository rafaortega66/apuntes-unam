En corto

  • strerror(n) devuelve la cadena del mensaje de sistema para el código n; perror("txt") imprime txt: <mensaje del sistema> si la instrucción anterior falló (la P es de "personalizar").
  • fork() abre tres caminos: error (-1), hijo (0) y padre (PID del hijo). Vive en <unistd.h> y devuelve pid_t (se imprime con %d).
  • Proceso huérfano = su padre ya murió pero él sigue vivo → lo adopta PID 1 (init/systemd); en Linux moderno hay subprocesos reapers que adoptan huérfanos, por eso a veces el PPID de adopción no es 1.
  • Familia exec (6 funciones): L = lista de args terminada en NULL · V = vector de punteros · E = entorno propio · P = busca en $PATH (no requiere ruta absoluta).
  • exec exitoso reemplaza la imagen del proceso: el original muere ahí y el código de abajo es inalcanzable. Si falla, devuelve -1 y el proceso sigue → hay que envolverlo en if + exit(EXIT_FAILURE).

🎯 Reglas y conceptos clave

  • Códigos de error del sistema: del 1 en adelante son errores; 0 es éxito (success).
  • El argumento 0 (argv[0]) de una llamada exec debe ser el nombre del ejecutable → por eso la cadena aparece repetida: execl("/bin/ls", "ls", "-l", "/", (char *)0).
  • Regla obligatoria: nunca dejar un exec "suelto". Envolverlo en if (... == -1) { perror(...); exit(EXIT_FAILURE); }.
  • Causa más común de que fork() devuelva -1: falta de memoria para duplicar la imagen del proceso.

strerror() y los códigos de error de Linux

strerror(n) — "devuelve el mensaje de sistema correspondiente al código que le pasas como parámetro". El prefijo str es por string: devuelve la cadena de texto asociada al código numérico. Análisis de programa03_codigos_sistema.c:

int i;
for (i = 0; i <= 150; i++)          /* el límite se puede subir a 200 para probar */
    printf("%d: %s\n", i, strerror(i));

%d (o %i) se reemplaza con el entero i; %s con el string que devuelve strerror(i).

  • Las distros comunes traen entre 130 y 133 códigos de error. En el entorno de clase (Fedora / Red Hat) el último con mensaje válido es el 133; a partir del 134 se imprime Unknown error.
  • En Fedora, el código 41 no tiene error asociado — está reservado / saltado para implementaciones futuras.

perror() — mensaje de error personalizado

Recibe una cadena personalizada; si la instrucción anterior generó error, perror toma esa cadena, le añade automáticamente ": " y concatena a la derecha el mensaje de error estándar del sistema. La P es de "personalizar".

Ejemplo: si un fork() falla, perror("fork") imprime fork: <mensaje del sistema>.

Control de flujo de fork()

Con condicionales, fork() abre tres caminos: el de error, el del hijo y el del padre.

Estilo compacto (paréntesis anidados):

if ((child = fork()) == -1) { ... }

El compilador lo resuelve así: 1) se invoca fork(); 2) su valor de retorno se asigna a child; 3) se compara child con -1.

Estilo descompuesto ("camino largo", prioriza claridad sobre rendimiento):

pid_t ch;
ch = fork();
if (ch == -1) { ... }

Documentación oficial y retorno de fork()

  • Para llegar al sitio oficial, buscar en Google: "Open Group" fork → www.opengroup.org.
  • fork(), getpid(), getppid(), getuid(), geteuid(), getgid(), getegid() están definidas en <unistd.h>.
  • fork() devuelve pid_t, que internamente es un entero → se imprime con %d.
  • Éxito: devuelve 0 al hijo y el PID del hijo al padre; ambos siguen ejecutando en paralelo las líneas posteriores.
  • Error: devuelve -1 al padre, no se crea hijo y se establece errno. Causa más común: falta de memoria para duplicar la imagen del proceso.

exit() y macros de salida

Cuando una llamada crítica (fork(), exec()) devuelve -1, se usa exit() para terminar el programa de inmediato y no seguir ejecutando código.

  • EXIT_FAILURE (en mayúsculas) ≡ exit(1) — salida no exitosa.
  • EXIT_SUCCESS ≡ exit(0) — salida exitosa.

Procesos huérfanos, adopción y reapers

Al correr programa08, la salida muestra in parent antes que in child, y el hijo, al llamar getppid(), obtiene 1 aunque su padre real era otro.

  • Proceso huérfano: "un proceso cuyo padre ya murió, pero él sigue vivo". Aquí el padre terminó antes de que el hijo llegara a getppid().
  • Linux no permite huérfanos sin control: el proceso PID 1 (init en sistemas antiguos, systemd en modernos) los adopta automáticamente.
  • En distros modernas hay subprocesos monitores llamados reapers ("recogedores") que adoptan y vigilan huérfanos para descargar al PID 1 → por eso a veces el PPID de adopción que ves no es 1.
  • Ver la distro exacta: cat /etc/os-release (la máquina del profesor: Fedora Linux Workstation 40).
  • Jerarquía familiar: el proceso creado es el hijo; el que llamó fork() es el padre; la terminal interactiva es el abuelo.

La familia de funciones exec

No existe exec "a secas": es una familia de seis funciones que empiezan con esa palabra y añaden 1 o 2 letras que definen su comportamiento.

LetraSignificado
L (list)Los argumentos se escriben como lista explícita separada por comas, terminada en NULL o (char *)0.
V (vector)Los argumentos van en un arreglo de punteros, también terminado en puntero nulo.
E (environment)Permite pasar un vector de variables de entorno propias, válidas solo durante la ejecución del nuevo proceso.
P (PATH)No requiere ruta absoluta: lee la variable PATH y busca el ejecutable en los directorios del sistema (/bin, /usr/bin…).
  • execl, execv, execle, execve → parámetro path (ruta absoluta, ej. /bin/ls).
  • execlp, execvp → parámetro file (nombre a secas, ej. ls).

Reemplazo de imagen y "argumento cero"

A diferencia de fork() (que duplica), cuando exec tiene éxito la imagen del proceso original en memoria se destruye y se reemplaza por completo por la del nuevo programa. El proceso original muere en ese punto y no recupera el control.

En C, argv[0] debe ser el nombre del ejecutable, por eso la cadena del comando aparece repetida:

execl("/bin/ls", "ls", "-l", "/", (char *)0);
/*     ^ruta      ^arg0 ^arg1 ^arg2  ^fin de lista */

Manejo de errores y código inalcanzable

Si el comando no existe o está mal escrito, exec falla, devuelve -1 y el proceso original sigue ejecutando las líneas de abajo. En una llamada exitosa, en cambio, esas líneas son inalcanzables (el proceso ya fue reemplazado).

Regla obligatoria — envolver en if y terminar si devuelve -1:

if (execl("/bin/ls", "ls", "-l", "/", (char *)0) == -1) {
    perror("execl");
    exit(EXIT_FAILURE);
}

Resultado: execl devuelve -1, perror("execl") imprime execl: No such file or directory y, como no hay exit, el proceso sigue vivo e imprime "esto no se imprime" — mostrando físicamente la falla por no manejar el error.
