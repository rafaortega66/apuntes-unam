# 6. Scheduling de tiempo real

## Planificabilidad

### Qué es
**Lo más importante al diseñar un sistema de tiempo real es saber si es planificable**: si todas sus tareas cumplen sus deadlines. Depende de **qué tareas hay**, de su **consumo** (C, tiempo de ejecución en el peor caso), de su **periodo** (T) y del **algoritmo de scheduling**.

## Los cuatro algoritmos de tiempo real
| Algoritmo | Cómo decide | Tipo |
|---|---|---|
| **Real-time executive** | A cada tarea se le asigna una **rebanada fija que se repite periódicamente**; hay que conocer las tareas de antemano | Estático |
| **Earliest Deadline First (EDF)** | Corre primero **la tarea con el deadline más cercano** | Dinámico |
| **Minimal Laxity First (MLF)** | Corre primero **la tarea con menor laxitud** (holgura) | Dinámico |
| **Resource reservation** | Al crearse, la tarea **anuncia sus requerimientos**; **si no es planificable, no se crea** | Control de admisión |
La diferencia entre EDF y MLF: EDF solo mira **cuándo se entrega**; MLF además **resta lo que falta por calcular**.

## 🎯 Minimal Laxity First

### La fórmula
!!! 🎯 Viene como ejercicio
El profesor resolvió MLF en el pizarrón con una línea de tiempo y dijo «si fuera examen…».
**Laxitud = tiempo que falta para el deadline − tiempo de ejecución que todavía falta.**
Gana la de **menor** laxitud. Se recalcula en cada instante (es dinámico).

### Ejercicio resuelto
P1: T = 50 ms, C = 25 ms. P2: T = 100 ms, C = 40 ms.
| Instante | Laxitud P1 | Laxitud P2 | Corre |
|---|---|---|---|
| t = 0 | 50 − 25 = **25** | 100 − 40 = 60 | P1 |
| t = 10 | (50 − 10) − 15 = **25** | (100 − 10) − 40 = 50 | P1 |
| t = 25 | P1 terminó | (100 − 25) − 40 = 35 | P2 |
| t = 50 | P1 despierta: 50 − 25 = **25** | (100 − 50) − 15 = 35 | P1 |
| t = 75 | P1 terminó | (100 − 75) − 15 = 10 | P2 (termina en 90) |
**Ambas cumplen.** Ojo: si calcular la laxitud le cuesta tiempo al scheduler en cada conmutación, ese costo se acumula y puede tumbar el sistema.
Error común: confundir la laxitud con el periodo.

!!! 😂 Para acordarte: el chihuahua enojado
«Tengo que terminar la práctica 7 hoy a las 8 de la noche y no le llego ni a la parada, o la de computación gráfica, que se entrega mañana… Para los proyectos finales: el de gráfica se entrega pasado mañana, pero sale en 20 minutos; el de embebidos, **ese pinche enano loco**, se entrega en dos semanas, **pero va a llevar las dos semanas completas**. ¿A cuál le dan? Al del **chihuahua Napoleón enojado** de embebidos.» Se atiende primero al que **menos holgura** deja, aunque se entregue después.

### Resource reservation
Cada tarea trae un encabezado con su **periodo** y su **consumo en el peor caso (WCET)**. Al crearla, el sistema hace una simulación rápida: si no cabe, **la rechaza** para no desestabilizar a las ya garantizadas. En tiempo real las tareas **no se crean al vuelo** como en un GPOS.

!!! 😂 Para acordarte: la tortillería
«Al principio la tarea dice: "Soy la tarea fulana, este es mi periodo y mi consumo peor esperado". Resource reservation hace una simulación breve: **"¿Cabes o no cabes? Si no cabes, te vas al carajo"**. ¿Qué pasa cuando llegan a las tortillas y están preparando un pedido para 40 personas? **"Regrese mañana."**»

## 🎯 La regla de oro

### La fórmula
!!! 🎯 Regla de oro
**Σ (Cᵢ / Tᵢ) ≤ 1**: la suma del consumo de cada tarea entre su periodo **no puede pasar de 1 (100 %)**. Si pasa, **no es planificable**, aunque la primera vuelta parezca acomodarse.

### Ejercicios
- **No planificable:** T1 (T = 50, C = 35), T2 (T = 50, C = 15), T3 (T = 100, C = 15): 35/50 + 15/50 + 15/100 = 70/100 + 30/100 + 15/100 = **115/100 = 1.15 > 1**. En la primera iteración no falla, pero en la segunda sí.
- **Sí planificable:** P1 (50, 25) y P2 (100, 40): 25/50 + 40/100 = 0.5 + 0.4 = **0.9 ≤ 1**.
Hazlo con **fracciones** (común denominador). Error común: revisar solo la primera vuelta de la gráfica.

!!! 😂 Para acordarte
«La suma de los consumos entre los periodos tiene que ser menor al 100 %. ¿Tendrá sentido? **No vas a cumplir si requieres más procesador que el que tienes, papá, no seas bruto.** Y aquí todos sacan la calculadora porque nunca aprendieron a hacer fracciones.» ¿Y si metes otro procesador? «Hay que decidir a qué procesador le asignas cada tarea, y si son codependientes, **ahí ya no se pudo**.»

### Por qué importa la prioridad
Con P1 (50, 25) y P2 (100, 40):
- **Si P1 tiene más prioridad:** P1 cumple su primer deadline (50) y el segundo (100), y P2 cumple el suyo (100). **Todo cumple.**
- **Si P2 tiene más prioridad:** P2 cumple, pero **P1 pierde su primer deadline**.
El mismo conjunto de tareas puede ser planificable o no **según cómo se asignen las prioridades**. Darle más prioridad a la de **periodo más corto** funciona: esa es la idea de Rate Monotonic.

## Rate Monotonic (RMS)

### Qué es
**Rate Monotonic** asigna **prioridades fijas** a las tareas periódicas para maximizar la planificabilidad, con una regla: **a menor periodo, mayor prioridad** (la tarea con el periodo más corto, obviamente, tiene menos tiempo disponible). Una tarea es planificable si al agregarla **todas** siguen siéndolo.
- **Es el algoritmo de scheduling estático óptimo:** si un conjunto de tareas no se puede planificar con RMS, **no lo planifica ningún algoritmo estático**.
- Pero **no optimiza el uso del procesador**.

!!! 😂 Para acordarte: el número de inscripción
«Los algoritmos estáticos asignan prioridades fijas: son como **su número de inscripción**. ¿Se imaginan que se los fueran cambiando durante las inscripciones? ¿Van a estar presionando **F5** todo el pinche día? Si de por sí se cae el sistema de inscripciones con 15,000 personas… En RMS el número que obtienen en primer semestre **se queda para toda la carrera**. Es conservador, pero las tareas no cambian: no son humanitos.»

### La cota del 70 %
**U ≤ n(2^(1/n) − 1)**, donde n es el número de tareas:
| Tareas (n) | Cota |
|---|---|
| 1 | 1.0 (100 %) |
| 2 | ≈ 0.828 (83 %) |
| 3 | ≈ 0.780 (78 %) |
| 4 | ≈ 0.757 (76 %) |
| n → ∞ | **ln 2 ≈ 0.693 (≈ 70 %)** |
La teoría dice que un conjunto de tareas puede usar **apenas el 70 % del procesador y aun así no todas cumplir sus deadlines**. Regla práctica: con RMS y varias tareas periódicas, **deja ~30 % de colchón**. Error común: querer operar un sistema de tiempo real al 99 o 100 %.

!!! 🎯 Lo que NO viene
**La demostración matemática de la cota no viene.** Sí: la fórmula, el criterio y que la cota baja hacia ~70 %.
