# 12. Linux embebido y construcción del kernel

## Desarrollo cruzado

### Tool chain
El **tool chain** es el conjunto de herramientas para construir el software: **compilador**, **enlazador** (*linker*), **ensamblador** y, si hay, **intérprete**. Se programa en una computadora de escritorio, pero el sistema de producción es **distinto en hardware, software y tool chain**: cambia el conjunto de instrucciones, y con él las librerías y las herramientas.
**Desarrollo cruzado:** cuando la plataforma de desarrollo (**host**) y la de producción (**target**) son diferentes. Hace falta un **tool chain cruzado** que corra en el host y genere ejecutables para el target; **todas las herramientas GNU lo soportan**. Ejemplo: la Práctica 8, compilar en la PC (x86) un kernel para la Raspberry Pi (ARM).
Hay que usar **control de versiones** (Git), con **etiquetas por versión** y las versiones de las librerías documentadas: si no, es casi imposible rastrear errores.

## Anatomía de Linux embebido

### Los cuatro elementos
1. **Kernel:** el **más maduro y estable**, escogido por sus características. **Rara vez se usa el último.** Hay que vigilarlo durante todo el desarrollo, suscrito a la lista de correo y de bugs de **kernel.org**.
2. **Drivers:** hay que tenerlos todos; **mejor un kernel que ya integre el driver que un driver propietario no probado**. Es común el **backport**: traer un driver nuevo a un kernel viejo y estable.
3. **Sistema operativo y plataforma:** personalizado (*Roll Your Own*) o una plataforma madura con soporte extendido. **Los SO de escritorio no sirven para embebidos.**
4. **Sistema de archivos raíz:** todos los programas y librerías, el intérprete (bash, sh) y el gestor de paquetes (**DPKG** de Debian o **RPM** de Red Hat).

!!! 🎯 Cómo se escoge el kernel
**Estable, maduro y probado (LTS)**, no el más nuevo. Una rama madura manda ≈ 2 avisos al año; una en desarrollo, hasta 30 al día. Cada parche se evalúa: ¿corrige algo que me afecta o rompe otra cosa?

!!! 😂 Para acordarte: el sugar maduro y Mbappé
«**Nos gustan maduros.** Eso de andar domando *brats* a nivel de código, no. Quieren uno que ya cojea un poco, necesita su insulina y es quejoso, **pero tiene trabajo estable, casa, coche, funciona y a las 10 de la noche ya se va a dormir**. Ya sé de qué pata cojea, le pongo su bastón y listo.»
El **backport**: «Necesito que el sugar me dure 20 años más: le abrimos el esternón, **tiramos el corazón podrido y le metemos uno nuevo**.»
El kernel nuevo: «Abren Tinder y ven un papacito de 18 años llamado **Mbappé**… pero viene con seis chamacos y paga dos pensiones. En embebidos mejor nos quedamos con el maduro.»

!!! 😂 Para acordarte: Doom en el kiosco
«Las distros de escritorio traen atajos como Alt+F4… **¿Cuántas veces no han visto Doom corriendo en un kiosco de McDonald's?** Llega el niño rata, conecta un teclado, abre una terminal y escribe `apt-get install`… "Comando no reconocido". Y empieza a echar espuma por la boca. **Es que el que hizo ese embebido salió de mi clase.**» Un embebido de producción va **sin gestor de paquetes, sin consola accesible y sin escritorio**.

### Paquetes y herramientas
**Un paquete incorrecto puede arruinar el sistema.** El diseñador escoge y **compila los paquetes desde cero** para su plataforma: **«no hay `sudo apt-get install`»**. Herramientas para generar un Linux embebido:
| Herramienta | Qué es |
|---|---|
| **Buildroot** | Makefiles y parches para generar el sistema |
| **Yocto Project** | Genera sistemas Linux personalizados; apoyado por la Linux Foundation |
| **OpenEmbedded** | Framework para crear distribuciones embebidas |
| **Linaro** | Construcción con generación automática |
Familias de distribuciones: **Debian** (Ubuntu, Mint, **Raspberry Pi OS**; `apt`) y **Red Hat** (Fedora; RPM con `dnf`).

## Construir un kernel

### Los pasos
1. **Descargar el árbol completo** del código fuente (el núcleo y los drivers de **todas** las arquitecturas: `/arch`, `/drivers`…).
2. **Escoger la arquitectura y las opciones** (qué controladores incluir). Arquitecturas: Intel x86, **ARM**, MIPS, PowerPC, SPARC, AVR32, Xtensa (la del ESP32) y muchas más.
3. **Compilar y generar la imagen**, normalmente **comprimida y en flash** (se descomprime en RAM al arrancar).
4. **Generar el sistema de archivos raíz**.
La configuración tiene **más de 5000 líneas: no se edita a mano**. Herramientas: **`make menuconfig`** (Y incluye, N excluye, M módulo), `make xconfig`, `make gconfig` y `make defconfig`. Si se necesitan muchos paquetes, **mejor partir de una distribución existente**.

### El archivo .config
| Línea | Significado |
|---|---|
| `CONFIG_FEATURE_XX=y` | **Integrada en el kernel**; no se actualiza sin actualizar el kernel |
| `#CONFIG_FEATURE_XX` | **Comentada**: no estará disponible |
| `CONFIG_FEATURE_XX=m` | **Módulo dinámico** |
**No todo puede ser módulo, y solo los drivers deberían serlo** (kernel pequeño y flexible). En embebidos, los módulos que no se usan se eliminan, y como el hardware es fijo, conviene **integrar (=y)** los drivers.

!!! 😂 Para acordarte: «me estoy bañando»
«Si pones M, al arrancar el kernel le pregunta al hardware: "¿Oye, estás ahí?" y el hardware le dice "**oye, me estoy bañando**"… y el kernel se va a jugar al bosque en lo que el driver está. En embebidos usamos Y, el hardware es idéntico: el kernel despierta y dice **"ya sé quién soy, tengo superpoderes y voy a volar"**.»
Y en la Práctica 8 cambiaban el logo de la frambuesa en el driver de video: «unos compañeros pusieron a **Henry Cavill**… tuve que echarme agua fría».

### El RootFS
Es **lo que se ve al iniciar sesión en la consola**: la jerarquía de directorios estándar (**FHS**, parte del LSB) con todos los paquetes, sus dependencias resueltas y sin conflictos. En UNIX hay **una sola raíz `/`**: no hay letras de unidad.
| Directorio | Contenido |
|---|---|
| `/bin` | Programas de usuario |
| `/dev` | Dispositivos de hardware y *pipes* de memoria |
| `/etc` | Configuración |
| `/lib` | Librerías compartidas (`.so`) |
| `/lib/modules` | Drivers como módulos del kernel |
| `/proc` | Procesos en ejecución (**virtual**) |
| `/root` | *Home* del root |
| `/sbin` | Programas de sistema, incluido el arranque |
| `/sys` | Dispositivos y drivers (**virtual**) |
| `/tmp` | Temporales |
| `/usr` | Programas instalados sobre la base |
| `/var` | Lo que cambia siempre; **en embebidos, en partición aparte** |

### El arranque
- **En embebidos conviene integrar el sistema de archivos raíz en la imagen del kernel**: arranca más rápido y los drivers se cargan antes (es la idea de initramfs).
- Ya cargado el rootfs en el RAM disk, **el kernel ejecuta `/init` como primer proceso** (un script o un ejecutable).
- **En un Linux tradicional**, **GRUB** trae un micro-kernel que carga los drivers de archivos y deja **elegir** la imagen del kernel y el rootfs; luego lo reemplaza por el kernel elegido.
- **En un embebido, GRUB es una pérdida de tiempo**: se cargan **directamente el kernel y el rootfs** a memoria.
- **BusyBox:** **un solo ejecutable pequeño** con versiones reducidas de muchas utilidades de UNIX; un entorno completo para sistemas pequeños.
- **Windows embebido y Android:** la presentación solo los muestra en imágenes; el dato clave es que **Android corre sobre un kernel de Linux**. Del Windows IoT el profesor dijo que no es embebido de verdad ni soporta tiempo real («nos da asco»).
